[[vertx:run]]
= *vertx:run*

This goal allows to run the Vert.x application as part of the Maven build, in a separate process.

By default, it monitors the `src/main` directory and, if the code changes, rebuilds the project and restarts the application.
The plugin re-executes the mojos that ran between the _generate-source_ and the _process-classes_ phases.

So, to start a Vert.x application, just launch:

[source]
----
mvn vertx:run
----

If the sources aren't compiled, the plugin executes `mvn compile` for you.

[[run-redeploy-filtering]]
== Redeploy filtering

You can fine-tune which file changes trigger a redeployment using `redeployIncludes` and `redeployExcludes`.
The patterns follow the https://ant.apache.org/manual/dirtasks.html#patterns[Ant-like] syntax and are relative to the `redeployRootDirectory`.

For example, if the project contains a web frontend built with Node in `/src/main/frontend`, you will have to exclude files that are changed as part of the frontend build:

[source,xml]
----
<plugin>
<groupId>io.reactiverse</groupId>
<artifactId>vertx-maven-plugin</artifactId>
<version>${vertx-maven-plugin.version}</version>
<executions>
  <execution>
    <id>vmp</id>
    <goals>
      <goal>initialize</goal>
      <goal>package</goal>
    </goals>
  </execution>
</executions>
<configuration>
  <redeployRootDirectory>${project.basedir}/src/main</redeployRootDirectory>
  <redeployExcludes>
    <redeployExclude>frontend/node_modules/**</redeployExclude>
    <redeployExclude>frontend/dist/**</redeployExclude>
    <redeployExclude>frontend/package-lock.json</redeployExclude>
  </redeployExcludes>
</configuration>
</plugin>
----

[[run-environment-variables]]
== Environment variables

You can set environment variables for the forked Vert.x application process using `environmentVariables`.

For example, to configure database connection details:

[source,xml]
----
<plugin>
<groupId>io.reactiverse</groupId>
<artifactId>vertx-maven-plugin</artifactId>
<version>${vertx-maven-plugin.version}</version>
<configuration>
  <environmentVariables>
    <DB_HOST>localhost</DB_HOST>
    <DB_PORT>5432</DB_PORT>
  </environmentVariables>
</configuration>
</plugin>
----

[[run-additional-classpath]]
== Additional classpath entries

You can add dependencies and classpath elements that are available at runtime but not part of the project's compile or runtime scope.
This is useful for development-only tools like logging backends, diagnostic libraries, or configuration directories.

=== Additional dependencies

Use `additionalDependencies` to declare Maven artifacts that will be resolved (with their transitive dependencies) and added to the classpath or module path of the running application.

For example, to add a Logback logging backend during development:

[source,xml]
----
<plugin>
<groupId>io.reactiverse</groupId>
<artifactId>vertx-maven-plugin</artifactId>
<version>${vertx-maven-plugin.version}</version>
<configuration>
  <additionalDependencies>
    <dependency>
      <groupId>ch.qos.logback</groupId>
      <artifactId>logback-classic</artifactId>
      <version>${logback.version}</version>
    </dependency>
  </additionalDependencies>
</configuration>
</plugin>
----

Exclusions are supported, just like regular Maven dependencies:

[source,xml]
----
<additionalDependencies>
  <dependency>
    <groupId>ch.qos.logback</groupId>
    <artifactId>logback-classic</artifactId>
    <version>${logback.version}</version>
    <exclusions>
      <exclusion>
        <groupId>org.slf4j</groupId>
        <artifactId>slf4j-api</artifactId>
      </exclusion>
    </exclusions>
  </dependency>
</additionalDependencies>
----

=== Additional classpath elements

Use `additionalClasspathElements` to add directories, JAR or ZIP files directly to the classpath.
This is handy for configuration files that should not be part of the project resources.

NOTE: `additionalClasspathElements` is only used in classpath mode.
When running on the <<run-module-path,module path>>, these entries are ignored.

For example, to add a directory with a development-specific logging configuration:

[source,xml]
----
<plugin>
<groupId>io.reactiverse</groupId>
<artifactId>vertx-maven-plugin</artifactId>
<version>${vertx-maven-plugin.version}</version>
<configuration>
  <additionalClasspathElements>
    <element>${project.basedir}/dev-config</element>
  </additionalClasspathElements>
</configuration>
</plugin>
----

[[run-toolchains]]
== Maven Toolchains

The `run` goal supports https://maven.apache.org/guides/mini/guide-using-toolchains.html[Maven Toolchains].
When a JDK toolchain is configured, the forked Vert.x application uses the toolchain JDK instead of the JDK running Maven.
This is useful when your code targets a higher JDK version than the one running Maven.

To use a JDK toolchain, first declare it in your `~/.m2/toolchains.xml`:

[source,xml]
----
<toolchains>
  <toolchain>
    <type>jdk</type>
    <provides>
      <version>21</version>
    </provides>
    <configuration>
      <jdkHome>/path/to/jdk-21</jdkHome>
    </configuration>
  </toolchain>
</toolchains>
----

Then activate the toolchain in your `pom.xml` using the `maven-toolchains-plugin`:

[source,xml]
----
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-toolchains-plugin</artifactId>
  <executions>
    <execution>
      <goals>
        <goal>toolchain</goal>
      </goals>
    </execution>
  </executions>
  <configuration>
    <toolchains>
      <jdk>
        <version>21</version>
      </jdk>
    </toolchains>
  </configuration>
</plugin>
----

When no toolchain is configured, the plugin falls back to the `java.home` system property and then the `JAVA_HOME` environment variable.

[[run-module-path]]
== Module path mode

When a Vert.x 5 project contains a `module-info.java` and uses a custom main class, the plugin automatically launches the application on the module path instead of the classpath.
All project dependencies are placed on the `--module-path` and the application is started with `--module`.

Module path mode is not compatible with loading verticles by class name (the `vertx.verticle` property).
When a verticle is specified, the launcher loads it by class name across module boundaries, which breaks JPMS encapsulation.
With a custom main class, the application's own module is the root module and verticles can be instantiated directly.

Module path mode is enabled automatically when all the following conditions are met:

- The project uses Vert.x 5
- The project has a compiled `module-info.class` in the classes directory
- No verticle is configured (the `vertx.verticle` property is not set)

To disable module path mode and force classpath mode, set `useModulePath` to `false`:

[source,xml]
----
<plugin>
<groupId>io.reactiverse</groupId>
<artifactId>vertx-maven-plugin</artifactId>
<version>${vertx-maven-plugin.version}</version>
<configuration>
  <useModulePath>false</useModulePath>
</configuration>
</plugin>
----

=== Example modular project

Your `module-info.java` should declare the required dependencies:

[source,java]
----
module com.example.myapp {
    requires io.vertx.core;
    requires io.vertx.launcher.application;
}
----

Your custom launcher extends `VertxApplication` and supplies the verticle instance directly, avoiding cross-module reflection:

[source,java]
----
package com.example.myapp;

import io.vertx.core.Verticle;
import io.vertx.launcher.application.VertxApplication;
import io.vertx.launcher.application.VertxApplicationHooks;

import java.util.function.Supplier;

public class CustomLauncher extends VertxApplication implements VertxApplicationHooks {

    public static void main(String[] args) {
        new CustomLauncher(args).launch();
    }

    public CustomLauncher(String[] args) {
        super(args);
    }

    @Override
    public Supplier<Verticle> verticleSupplier() {
        return MyVerticle::new;
    }
}
----

NOTE: Using `VertxApplication` and `VertxApplicationHooks` is not mandatory.
Any class with a `public static void main(String[])` method works as a custom launcher.

Configure the plugin to use your custom launcher:

[source,xml]
----
<properties>
  <vertx.launcher>com.example.myapp.CustomLauncher</vertx.launcher>
</properties>
----

With the default `useModulePath` value (`auto`), the plugin detects the module descriptor and launches the application with `--module-path` and `--module`.

=== Passing JPMS flags

If your application or its dependencies require additional JPMS flags (such as `--add-opens`, `--add-exports`, `--add-reads`, or `--add-modules`), pass them via `jvmArgs`:

[source,xml]
----
<plugin>
<groupId>io.reactiverse</groupId>
<artifactId>vertx-maven-plugin</artifactId>
<version>${vertx-maven-plugin.version}</version>
<configuration>
  <jvmArgs>
    <arg>--add-opens=java.base/java.lang=ALL-UNNAMED</arg>
    <arg>--add-exports=java.base/sun.nio.ch=ALL-UNNAMED</arg>
  </jvmArgs>
</configuration>
</plugin>
----

=== Non-modular dependencies

Dependencies that do not contain a `module-info.class` are placed on the module path as _automatic modules_.
The JVM derives their module name from the JAR filename or the `Automatic-Module-Name` manifest entry.
This works transparently in most cases.
